PERSONAL PROJECT · LOCAL DOCUMENT QA APPLICATION

Document QA with inspectable sources

A question-answering application for multiple PDFs, including text, tables, and figures, with answers linked to the original source pages.

My contribution. I built the application across a FastAPI backend, document parsing and vector retrieval, and a Streamlit interface for inspecting cited pages. It supports Ollama for local chat and embeddings; table and figure descriptions use Gemini.

Python / FastAPILangChainDoclingChromaStreamlitOllama
Architecture and engineering notes

Document ingestion

  1. Upload PDFsStreamlit interface → FastAPI
  2. Parse and describeDocling extracts content; Gemini describes tables and figures
  3. Chunk and embedContextual chunks with headings and page metadata
  4. Store the indexPersistent Chroma vectors and SQLite document records

Question answering

  1. Ask a questionFastAPI loads the session's chat history
  2. Retrieve passagesChroma returns the three most relevant chunks
  3. Generate an answerLangChain assembles context for Ollama or Google models
  4. Inspect the evidenceSource references open the corresponding PDF page
Traceable sources
Chunks retain the source document, headings, and page numbers. The interface displays retrieved references beside the answer so readers can check the original page.
Persistent state
Chroma stores the vector index; SQLite stores document records and chat history. FastAPI exposes upload, list, delete, chat, and PDF retrieval endpoints.
Reusable processing
Document conversions, table and figure descriptions, and chunks are cached on disk to reuse completed ingestion steps.
Inspecting model behavior
LangSmith instrumentation traces retrieval and model calls with session and model metadata.

Current scope: A locally run personal project. Ollama supports local chat and embeddings; ingestion still uses Gemini for table and figure descriptions.

HPI · COLLABORATIVE RESEARCH SOFTWARE

MaskBench

A benchmark framework that measures how masking affects pose-estimation accuracy and motion fidelity. It gives researchers a repeatable way to compare masking strategies and select an approach for behavioral analysis.

My contribution. I co-developed the benchmarking infrastructure, integrating 7+ pose-estimation models and parallelized, cached processing for 100GB+ video datasets.

Pose estimationBenchmarkingPython
Architecture and evaluation
  1. DatasetVideos and optional ground-truth poses
  2. Inference engineYOLO, MediaPipe, OpenPose, and MaskAnyone variants
  3. EvaluatorPCK, RMSE, distance, velocity, acceleration, and jerk
  4. VisualizerResult tables, pose plots, and timing comparisons
Reusable runs
Checkpoints retain intermediate results; the renderer produces annotated videos for inspection.
MaskAnyone integration
The connected pipeline uses YOLO detection and SAM2 segmentation with OpenPose or MediaPipe pose estimation.
Collaboration
Collaborators include Tim Riedel, Zainab Zafari, Wim Pouw, and Gerard de Melo.

03

OPEN-SOURCE CONTRIBUTION · PRIVACY-PRESERVING AI

MaskAnyone

A web-based toolbox that combines video and audio masking techniques while retaining information useful for behavioral analysis.

My contribution. I help maintain, improve, and test the open-source video de-identification software.

Video de-identificationFastAPIReactDocker
Masking strategies and analytic utility
Blur
Softens visual detail.
Pixelation
Replaces detail with pixel blocks.
Contours
Represents the subject through outlines.
Solid fill
Replaces subject appearance with flat regions.

The research question is which information each strategy retains for behavioral analysis. The published MaskBench comparison used three source videos and found that pose-estimation performance depended on the masking strategy and estimator.
